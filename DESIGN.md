# B站社交圈 (BiliSocial) — build contract

Chrome MV3 extension, plain JavaScript, no build step, no npm dependencies at runtime. Every agent working on this repo reads this file first and stays inside the files it owns. User-facing text is Simplified Chinese, plain words; code, comments and commits are English.

## Reference project

The sibling extension [MoonDigest](https://github.com/PathGao/MoonDigest) (`extension/`) is the style and pattern source:
- Visual style: `tokens.css` (Bilibili-modern palette, light/dark), `triage/triage.html` + `triage/triage.css` (full-page app layout), `options.css`. Copy tokens.css verbatim into this repo and build on it. One filled blue button per view, pink = where you are.
- Background B站 fetch: `triage/triage-bg.js` (`triageBiliGet`, `triageBiliPost` with `bili_jct` csrf from `chrome.cookies`), WBI signing in `sites.js` (`biliMixinKey`, `biliWbiSign`, `biliMd5`).
- AI tagging prompt: `triageBuildCommandMessages` / `triageParseCommand` in `triage/triage-bg.js`; AI provider handling in `background.js`.
- Dev harness for pages without a real extension: `triage/dev/mock-chrome.js`, `dev-sidepanel/`.
- Self-tests: `*.selftest.js`, run with `node <file>`.

## Layout and ownership

```
extension/

  tokens.css               core (copy of MoonDigest tokens.css)
  icons/                   integration
  background.js            core: message router + job runner; other agents add ONE importScripts line + ONE router case each
  lib/bili.js              core: B站 API client (throttle queue, WBI, retries)
  lib/store.js             core: chrome.storage.local helpers (get/set/patch, keys below)
  lib/jobs.js              core: resumable crawl jobs
  lib/ai.js                follow agent: OpenAI-compatible chat + UP tagging prompt/parse
  lib/push.js              follow agent: alarms + notifications for tagged UPs
  lib/graph.js             graph agent: similarity + clustering + layout data (pure functions, also runs under node)
  lib/graph-ai.js          graph agent: bs-ai-name-groups (AI names for 圈子, via Ai.chat)
  app.html / app.css / app.js   core: shell, top nav, hash router, shared UI helpers
  pages/follow.js          follow agent  (#follow, UP 主管理)
  pages/fans.js            follow agent  (#fans, 粉丝)
  pages/graph.js           graph agent   (#graph, 关系图)
  pages/me.js              me agent      (#me, 我的位置) + pages/me.css; lib/me.js scoring + bs-stat (page and worker)
  pages/settings.js        follow agent  (#settings, 设置: AI, 阈值, 推送)
  pages/feed.js            feed agent    (#feed, 动态: 关注 video feed by tag) + pages/feed.css; lib/feed.js bs-feed page cache (worker)
  content/badges.js        feed agent: tag chips on B站 pages (www/search/t/space.bilibili.com), styles inline in the script
  dev/index.html, dev/mock-chrome.js, dev/make-fixtures.mjs   core
  (fixtures live outside the extension: BiliSocial/dev-fixtures/, synthetic data generated by make-fixtures.mjs, gitignored,
   never inside extension/ where a loaded extension would carry it)
  *.selftest.js            each agent for its own files
```

`app.js` exposes `window.BS = { send, get, onStore, esc, toast, confirm, fmtAgo, fmtCount, avatar, route }`; each page file registers `BS.page("follow", { mount(el), unmount() })`. Pages read data straight from `chrome.storage.local` (via `BS.get`) and re-render on `chrome.storage.onChanged` (via `BS.onStore`). Pages call the background only for jobs and writes.

## Storage (chrome.storage.local, `unlimitedStorage`)

| key | shape |
|---|---|
| `bs_me` | `{ mid, name, face, sign, following, follower, at }` |
| `bs_people` | `{ [mid]: { mid, name, face, sign, ov, gone? } }` — every account seen anywhere. A placeholder (empty name, 「账号已注销」, default noface.jpg) never replaces a known name/face; `gone: true` = B站 shows the account as closed (name/face are the last real ones) |
| `bs_followings` | `{ at, list: [mid], followTime: { [mid]: sec }, special: { [mid]: 1 }, groups: { [mid]: [tagid] } }` — mine, newest first; `followTime` is when I followed them (API `mtime`); `special` = in 特别关注 (group -10); `groups` = the account's own groups (tagid ≥ 0, only non-empty), used to take it out of 特别关注 |
| `bs_fans` | `{ at, list: [{ mid, followTime, mutual }], lost: [{ mid, at, followTime }] }` — `lost` = fans gone since the previous `mine` sync, newest first (≤500), `at` = the sync that noticed; one who follows again leaves it. When B站 returns only part of the list, only fans newer than the oldest returned one can count as lost. #fans shows 最近取关我的 |
| `bs_circle` | `{ [mid]: { code, total, list: [mid], plain, same, sameAt, at, checkedAt } }` — followings of each of my followings; code 22115 = hidden. B站 gives only the newest 100 of someone else's list: those come first in `list` (`plain` of them; absent = all of `list`). A cut list (`total` > `plain`) then gets the account's followings I follow too from `same/followings` (not capped), appended without duplicates; `same` = how many that returned, `sameAt` = when. `checkedAt` = last time the job asked B站 about the account (`at` on older records) |
| `bs_last_post` | `{ at, since, map: { [mid]: sec } }` — newest post per account from the video feed paged back past slowDays (content job phase 1); `since` = oldest feed item seen |
| `bs_content` | `{ [mid]: { code, count, tlist: {分区: n}, v: [{ t, tid, c, p, len }], at } }` — latest 30 videos |
| `bs_interactions` | `{ at, videos: [{ bvid, aid, title, play, dynId, at }], byMid: { [mid]: { pm: { count, first, last }, reply, like, atMe, comments, repostComments, reposts: [{ bvid, dynId, at }], span: { [field]: { first, last } }, last } } }` — `comments` = under my videos incl. sub-replies, `repostComments` = under other people's reposts of my videos; `span` has an entry for each of reply/like/atMe/comments/repostComments with count > 0 |
| `bs_up_tags` | `[{ id, name, color, rule, push }]` |
| `bs_up_tag_map` | `{ [mid]: [tagId] }` |
| `bs_unfollowed` | `{ [mid]: { at, tagIds, source } }` — for 重新关注; `source`: `"app"` = 取关 here (bs-follow act 2; records without `source` are older app records), `"bili"` = a complete `mine` sync found the account gone from my followings (unfollowed on B站 or the phone), tags moved from `bs_up_tag_map` into `tagIds`. A sync removes the record (and puts the tags back) only when B站's follow time (`mtime`) is newer than `at`; otherwise the account stays out of `bs_followings.list` |
| `bs_settings` | `{ ai: { baseUrl, apiKey, model }, alpha: 0.5, slowDays: 90, deadDays: 365, pushMinutes: 15 }` |
| `bs_jobs` | `{ [job]: { running, done, total, step, startedAt, finishedAt, lastFinishedAt, error, throttled, cursor, hold, after, beat } }` — `beat` = last heartbeat (unix sec, an answered request or progress, at most every 20 s) — `finishedAt` is cleared when the job starts again, `lastFinishedAt` (last successful finish) never is: use it for "has finished once" — `step` is plain Chinese ("第 2/2 步 · 查每个人的投稿"); the shell shows 「正在{step} {done}/{total} · 还要约 N 分钟」. `hold: { until, why: "throttled"\|"network", n, of }` while the shared queue waits out a pause (show it only while `until` > now: 「被 B站 限流，85 秒后重试」). `after: "content"` on circle = queued, starts by itself when 投稿内容 finishes or is stopped (not after an error). `skipped` (content) = accounts B站 answered with a temporary error this run (not stored, asked again next run); the step text then ends with 「（N 个暂时没查到，下次再查）」 |
| `bs_interactions_work` | interactions job's working state for resume, and after a finish the per-unit results 更新 reuses; pages ignore it |
| `bs_stats` | `{ [mid]: { follower, at } }` — follower counts for #me, 7-day cache, written by `bs-stat` |
| `bs_group_names` | `{ [key]: { name, desc, mids, by: "ai" or "me", at } }` — 关系图 圈子 names; key = sorted top-5 member mids, `mids` = top 15; a group sharing >half of `mids` keeps the name (`BSGraph.groupName`). Written by the graph page |

Times are unix seconds. mids are strings.

## Messages (`chrome.runtime.sendMessage({ type, ... })` → `{ ok, data?, error? }`)

| type | effect |
|---|---|
| `bs-job-start` `{ job }` | start/resume a job: `mine` (me + followings + fans + profiles), `circle`, `content`, `interactions` |
| `bs-job-stop` `{ job }` | stop now (the request in flight is dropped); on a queued job, take it out of the queue |
| `bs-follow` `{ mid, act }` | act 1 follow, 2 unfollow (POST `x/relation/modify`, csrf). Also keeps `bs_followings` and `bs_unfollowed` in step: act 2 adds `{ at, tagIds, source: "app" }` unless a record exists (leaves `bs_up_tag_map` to the page); act 1 deletes the record and restores its live tags where the map has none. Safe to repeat |
| `bs-special` `{ mid, on }` | 特别关注 on/off for an account in `bs_followings.list` (else error). on: POST `x/relation/tags/copyUsers` `fids=mid&tagids=-10`; off: POST `x/relation/tags/moveUsers` `fids=mid&beforeTagids=-10&afterTagids=<groups[mid] or 0>` (stays followed). Then updates `bs_followings.special`; the page never writes it |
| `bs-ai-tag` `{ instruction, mids }` | follow agent: returns proposal `{ newTags, assignments, note }`, writes nothing |
| `bs-push-test` | follow agent: one notification to check permission |
| `bs-stat` `{ mids }` | me agent: `{ [mid]: follower }` for ≤50 mids via `x/relation/stat`, cached in `bs_stats`; saved one by one |
| `bs-feed` `{ offset }` | feed agent: one page of the 关注 video feed `{ items: [{ bvid, title, cover, duration, play, mid, name, face, at }], offset, hasMore }`; pages cached 5 min in memory + `chrome.storage.session` `bs_feed_cache` (not local) |
| `bs-open-app` `{ hash }` | feed agent: opens `app.html#<hash>` in a new tab (the chips on B站 pages use `feed?tag=<id>`) |
| `bs-ai-name-groups` `{ groups: [{ key, zones, members: [{ name, sign, titles }] }] }` | graph agent: `{ names: [{ key, name, desc }] }` from the configured AI, writes nothing; error `NO_AI` when AI is not set |

Job progress is written to `bs_jobs`; pages watch it. Errors also carry `code` (`"THROTTLED"`, `"NOT_LOGGED_IN"`, or a B站 number). `bs-follow` also updates `bs_followings` (adds to the front / removes, and drops `special`/`groups` on unfollow) and `bs_unfollowed` (see above); a page that still writes `bs_unfollowed` itself keeps working.

## Core interfaces (as built)

- `mine` compares the new followings list with the stored one (`Jobs.followDiff`): see `bs_unfollowed`. Follows made through bs-follow after the sync started are kept even if B站's list lags; unfollows made here stay out. A list B站 cut short (fewer than `total`) marks nobody as unfollowed.
- 投稿内容 stores a per-account error code only when it means the account is gone (-404, -626); other codes, HTTP errors and WBI rejections are counted in `skipped` and retried next run. Records from older builds with other codes are asked again.
- `Bili`: a WBI rejection (-403) refetches the mixin key and retries once; a risk answer on a signed call drops the key before the retry. A success answer with an empty list where one is expected (followings/followers page 1, video feed first page, arc/search with count > 0) is asked once more after 1.5 s.
- Install/update/reload: background injects the manifest's content scripts into open B站 tabs (`scripting` permission); the fresh `badges.js` fires `bsc-superseded` on `document` and the old copy removes its chips and listeners. A copy whose `chrome.runtime.id` is gone stops by itself and lets the click through. Chips carry a grey left marker and the tooltip 「B站社交圈的标签 · 只存在扩展里」.
- Background globals (importScripts): `Bili` (lib/bili.js), `Store` (lib/store.js), `Jobs` (lib/jobs.js).
  - `Bili.*` endpoint functions return plain data and go through the global ~1 req/s queue with risk back-off: `nav, relationStat, userCards, followings, sameFollowings, followers, arcSearch, feedVideo, feedUpdate, spaceDynamics, forwards, dynDetail, replies, subReplies, msgfeed, unread, sessions, sessionMsgs, modifyRelation, copyUsers, moveUsers`. A B站 code ≠ 0 throws an Error with that numeric `code` (except `followings` and `sameFollowings`, which return `{ code }`; its items also carry `special` and `groups`); 3 risk answers in a row throw `code: "THROTTLED"`. A risk answer or a dropped connection pauses the whole queue (every job), reported through `Bili.onHold`; dropped connections and requests with no answer in 30 s (aborted) retry for ~10 minutes before `code: "NETWORK"`. `feedVideo`/`spaceDynamics` items: `{ dynId, mid, name, face, at, bvid, aid, title, cover, play, forwards, comments }`.
  - `Store.get(key, fallback)`, `set`, `patch(key, entries)` (shallow merge into a map), `patchIn(key, id, fields)`, `update(key, fn)`; read-modify-write calls on one key are serialized.
- Worker keep-alive: while a job runs, an extension API call every 20 s plus a 1-minute `bs-keepalive` alarm; on wake (and on browser startup) `Jobs.resumeAll()` restarts jobs still marked running. It is also the watchdog: a job in memory marked running whose `beat` is over 3 minutes old, with no queue pause (`hold`) in the last minute, is dropped and started again from its cursor (once; a fresh run writes a new beat). circle/content write their results every 5 accounts or 15 s. A job started again after a stop resumes; one started after it finished starts over (content always skips accounts already stored, circle runs by the rule below; a re-run of interactions keeps the old `bs_interactions` until the new scan is complete).
- Interactions 更新 (`bs-job-start { job: "interactions" }` after a finish) redoes only what changed, with the same counts as a full scan: a video whose comment count is unchanged keeps its comments, its repost list is reused when the repost count is unchanged, and each repost's comment area is checked with one `dynDetail` and re-scanned only if its count changed; notifications (`msgfeed` items carry `id`) are kept by item id and paged from the newest until the first known item with the same time; the session list is read in full and only sessions whose `session_ts` changed are counted again. `opts: { full: true }` (panel 「完整重扫」) starts from nothing. Known gaps of 更新: a deleted comment plus a new one at equal counts, and notifications B站 has since expired stay counted.
- 关注的关注 has three modes, fixed when a run starts and kept in its cursor (`{ mode, phase }`), so a resumed run keeps it. `new` (first run, and the automatic run for new follows after 投稿内容, `opts.newOnly`): only accounts not stored. `update` (the button 「更新关注的关注」 after a finish): each stored public list gets page 1 only; the entries before the first stored mid are new follows, and when `total` = stored `total` + their number (and the stored plain part was whole, min(total, 100)) nothing was removed: 1 request, new ones on top, still ≤100. Otherwise (a removal, >50 new, became hidden) that plain list is fetched again (≤2 pages) and the common follows part is kept. Hidden lists are asked again only when `checkedAt` is 30 days old. Follows not stored get the whole list; accounts I no longer follow are left as they are and not asked. `full` (「全部重查」, `opts.full`): every list again. Phase 2 (「补共同关注」) asks `same/followings` for every cut list: in `new` only those without `sameAt` (this also fills records from older builds), otherwise all of them. A run resumed after a kill skips accounts with `checkedAt` / `sameAt` since the run started. Step text: 「更新关注的关注 · 第 1/2 步 · 只查第一页」, 「… · 第 2/2 步 · 补共同关注」.
- Job order: 投稿内容 goes before 关注的关注 (`after` above). A finished `mine` starts 投稿内容 if there is none yet; a finished 关注的关注 starts 投稿内容 again when it found second-layer accounts without content.
- `BS.onStore` listeners added during a page's `mount` are removed when the page unmounts. `BS.get("key")` returns the value, `BS.get([...])` an object. `BS.send` throws `Error(error)` with `.code`.
- Page stylesheets and shared page scripts (`vendor/d3.min.js`, `lib/graph.js`) go at the marked spots in `app.html` and `dev/index.html` (one line each; the owning agent adds them).
- Dev: `node extension/dev/make-fixtures.mjs` writes synthetic `BiliSocial/dev-fixtures/storage.json` (for node) and `storage.js` (for `dev/index.html`); `?real` reads `dev-fixtures/real-storage.js` (a local snapshot of your own storage, if you make one; never commit it). `file://` cannot load the scripts in the Browser pane; serve the repo root (`BiliSocial/`) with `python3 -m http.server` and open `/extension/dev/index.html` (it loads `../../dev-fixtures/`). Fake jobs move like real ones: `?sync` puts the fake fixture mid-sync (content + interactions running, circle queued), `?hold` adds a 90 s 限流 pause; running jobs in `?real` keep moving.

## B站 endpoints (all verified 2026-10-08 with the user's login)

- me: `x/web-interface/nav`, `x/relation/stat?vmid=`
- followings: `x/relation/followings?vmid=&pn=&ps=50` (own: all pages; others: only the newest 100 = 2 pages, later pages come back empty; hidden → code 22115). Measured: 136 of 475 public lists are cut at 100 (totals 102 to 4933)
- common follows: `x/relation/same/followings?vmid=&pn=&ps=50` = the account's followings that I follow too, not capped at 100 (account with 2923 follows, 3 of mine in its first 100 → total 67, all returned); hidden → 22115
- fans: `x/relation/followers?vmid=&pn=&ps=50`
- videos + 分区: `x/space/wbi/arc/search` (WBI signed; params `mid, ps=30, pn=1, order=pubdate, platform=web, web_location=1550101`)
- video feed: `x/polymer/web-dynamic/v1/feed/all?type=video&offset=`, cheap check `.../feed/all/update?type=video&update_baseline=`
- my dynamics: `x/polymer/web-dynamic/v1/feed/space?host_mid=&offset=`; reposts: `.../detail/forward?id=&offset=` (author in `item.user`); dynamic detail `.../detail?id=` (`basic.comment_id_str`, `basic.comment_type`)
- comments: `x/v2/reply?type=&oid=&pn=&ps=20&sort=0`, sub: `x/v2/reply/reply?type=&oid=&root=&pn=&ps=20`
- notifications: `x/msgfeed/reply|like|at` with cursor paging (`id` + `reply_time`/`like_time`/`at_time`), `x/msgfeed/unread`
- PM: `api.vc.bilibili.com/session_svr/v1/session_svr/get_sessions?session_type=1&group_fold=1&unfollow_fold=0&sort_rule=2&end_ts=`, `api.vc.bilibili.com/svr_sync/v1/svr_sync/fetch_session_msgs?talker_id=&session_type=1&size=50&end_seqno=`, names via `api.vc.bilibili.com/account/v1/user/cards?uids=`
- B站 notifications miss things: a big UP commented under the user's video and under his own repost, and none of it is in `msgfeed/reply`. The interactions job must scan the user's own videos' comment areas, each video's repost list, and the comment areas of those reposts.
- Risk control: HTTP 412 or code -352/-412/-799 (bili.js also counts -509) → pause the queue 90 s, stop after 3 in a row and record `throttled` in `bs_jobs`. ~1 request/s with jitter was safe for ~5000 requests.

## Similarity (graph)

Ported from an earlier prototype script (`build.js` + `graph.template.html`, not in this repo). Social part = co-citation + bibliographic coupling with 1/log(2+deg) weights, stopwords = accounts followed by >10% of crawled lists and B站 official service accounts (name regex in build.js). Content part = 0.4 typeid cosine + 0.6 title-bigram TF-IDF cosine. Mixed with `alpha` (social share), missing side carries full weight. kNN K=6 links, label propagation clusters, groups <12 → 零散. Layout: d3-force with per-cluster anchors on a golden-angle spiral (see template). Bundle d3 locally (copy `d3.min.js` v7 into `extension/vendor/`; MV3 forbids remote code).

Measured 2026-10-08 on the full data (agreement with B站 「知名X UP主」 labels, top-3 neighbours): social only 31%, content only 70%, alpha 0.5 → 69%. Default `alpha` is 0.5.

## Parallel work etiquette

- Three agents work at once in the same checkout. Stage only your own paths (`git add <your files>`), never `git add -A`, and commit with `git commit -- <paths>` semantics. If a commit fails because of someone else's staged files, unstage nothing of theirs; just commit your paths.
- Dev server: each agent serves `extension/` on its own port: follow 8701, graph 8702, me 8703 (`python3 -m http.server <port>` run in the background; stop it when done).
- Built-in Browser pane: open your own tab with `mcp__Claude_Browser__tabs_create` and pass that `tabId` to every browser call; never close or drive another agent's tab.
- Edits to shared files (`app.html`, `dev/index.html`, `background.js`) are single-line insertions at the marked spots via the Edit tool; re-read the file right before editing.

## Rules for every agent

- No write requests to B站 during development: never call follow/unfollow, never send a PM. Read-only live checks are allowed but keep each agent under 100 requests; the user's account is real.
- No new runtime dependencies. Dev scripts may use node built-ins.
- Do not touch files owned by another agent, except the one importScripts line and router case in background.js.
- Each agent leaves a selftest for its non-trivial logic and runs it.
- Commit your own files on `main` with a clear English message, author as configured in the repo. Never add Claude or any AI as co-author. Do not push; there is no remote.
